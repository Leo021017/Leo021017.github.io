Lab1: Xv6 and Unix utilities

sleep

xv6已经为我们实现了sleep函数的系统调用，并包含在头文件user/user.h中，直接使用即可

pingpong

管道（pipe）用于进程间通信（PIC），相当于一个内核中的文件缓冲区，两个进程共享这个缓冲区，通过读写共享信息

注意开的两个管道分别是A到B和B到A两个流向，一个管道负责子进程写父进程读，另一个管道负责父进程写子进程读，最后记得close不需要的文件描述符

父子进程最后需要exit(0)退出

由于我们把每个进程的读管道的写端都关闭了，所以read函数就不会再堵塞（注意子进程和父进程对同一个管道的写端和读端都是独立的，子进程不堵塞就要关闭子进程的写端）

但其实一个管道也可以

注：这里为了复习一下xv6手册中，使用了通过复制文件描述符将管道的读/写端重定向到标准输入/出的方式，当然可以对管道进行直接读写

primes

实验手册已经给出了实现原理图，每一个方块就是一个进程，方块之间的连接通过管道实现。第一个方块是父进程，用于生成35个连续的整数，然后递归往下生成子进程（is_prime函数），每个子进程的任务就是从管道pl读入父进程传进来的数，然后进行一轮判断，将剩下的整数继续生成一个进程和管道pr，然后传入pr

判断素数的伪代码手册已经给出

find

跟ls的区别就是find需要对每个文件名进行判断，还需要对路径下的文件夹也递归查找一遍

xargs

这里的难点就是对参数数组args的构建，这是一个指针数组，每个元素需要先malloc一片空间再使用，前几个参数通过argv数组读入，而传入的所有参数可以都放到args的一个元素中

Lab2: System calls

system call tracing

Lab1的几个实验是利用xv6内核已经实现的系统调用进行二次封装，而在这里我们需要真正地通过修改内核来添加一个系统调用

**实验目的：**实现一个叫做trace的系统调用，作用是对掩码参数指定的系统调用进行追踪，在每个系统调用返回时打印一条语句来输出调用该系统调用的进程的相关信息

SYS_wait是3，1 << SYS_wait就是100，即SYS_wait的掩码参数。同理，001就代表SYS_fork的掩码参数

在实现这个系统调用前，我们先讲清楚xv6是怎么把一个系统调用暴露给用户空间的

https://www.cnblogs.com/YuanZiming/p/14218997.html

  1. 用户程序调用user/user.h提供的系统调用接口int trace(int)

  2. 在用户空间这一侧，对接口的实现是一段汇编代码完成的（user/usys.S）

    代码逻辑是将SYS_trace的系统调用号（22）放入a7寄存器，使用risc-v提供的ecall指令（相当于x86的INT指令）将用户态转到内核态（由硬件支持）

    这段汇编由perl脚本（user/usys.pl）自动生成（make编译时）

  3. 内核空间这一侧的入口点是kernel/syscall.c中的syscall函数

    函数首先从a7寄存器中获取系统调用号，然后从一个函数指针数组中遍历到相应的系统调用实现函数（在kernel/proc.c中），最后将系统调用的返回值存放在a0寄存器中

  4. 最后由上面汇编中的ret指令从内核空间返回用户空间

先分析trace主程序的代码（user/trace.c），逻辑是先调用系统调用trace给当前进程加上mask，然后调用exec执行参数中包含的程序，后续在调用系统调用时就会进行跟踪

下面是具体的实验过程：

先在用户侧注册接口：① 修改user/user.h ② 修改user/usys.pl

trace通过一个掩码参数指定要追踪的系统调用，所以保存进程信息的proc结构体中应该加一个新的成员变量来存储掩码参数（kernel/proc.h）

kernel/sysproc.c里面是系统调用的具体实现，由于我们是调用trace后追踪进程中其他的系统调用，所以追踪信息并输出的部分应该放在去调用各种系统调用的函数中，这里只把掩码参数存入proc结构体中即可

argint函数可以读取调用系统调用时输入的参数，myproc函数通过查看当前cpu上运行的进程返回当前进程

实验要求可以trace可以追踪子进程，所以我们需要把mask从父进程复制到子进程中（kernel/proc.c）

xv6通过kernel/syscall.c中的syscall函数来调用kernel/sysproc.c中的系统调用函数，在这里加一个对mask参数的判断即可，注意判断语句不能用==而应该用&，因为掩码全1时要追踪所以系统调用

注意需要注册一个extern uint 64 sys_trace(void)和[SYS_ trace] sys_trace

这样，调用了trace的进程每一次调用其他系统调用都会执行这个判断，而没有调用trace的进程mask为0

另外记得在kernel/syscall.h中加上新的系统调用号

sysinfo

**实验目的：**添加一个系统调用sysinfo，需要获取两条信息：① 空闲内存的字节数 ② state字段不为UNUSED的进程数（不用写用户程序，由测试程序直接调用）

下面是实验过程：

和上面一样，在user/user.h、user/usys.pl和kernel/syscall.h注册sysinfo系统调用

在kernel/sysproc.c中实现系统调用

实验要求的两条信息在内核空间可以轻易获取，但xv6中用户态和内核态的数据并不能直接交互，那么怎么把这两条内核空间的数据传到用户空间呢？实验手册提示我们查看kernel/file.c中的copyout函数，通过注释我们可以看出copyout可以将给定地址（内核区）的数据拷贝到指定的进程页表（用户区）中，仿照sys_fstat()（kernel/sysfile.c）写出我们需要的拷贝语句

现在的两个关键点是两条信息的获取

  1. 获取空闲内存的字节数

    通过查看的数据结构我们发现空闲内存页由一个链表freelist来维护，一个页的大小是PGSIZE

    通过链表元素的数量就可以知道空闲内存的字节数

    看到别人用了acquire(&kmem.lock); 和release(&kmem.lock);在访问freelist前后进行了上锁，这样可以防止数据竞态

  2. 获取state字段不为UNUSED的进程数

    通过查看kernel/proc.c可以发现，64个进程的信息都存储在struct proc proc[NPROC]中，并且在procinit中对整个数组进行了初始化，遍历这个进程列表不会出现空指针异常

About XV6

So why did we need exit() in xv6?

Because, when building a program with gcc for linux for instance, the tool chain add the required exit call: see https://en.wikipedia.org/wiki/Crt0

In short, on linux, your program don’t start at main but at start:

On xv6, on contrary, the real starting point is main when OS try to return from main, it has no address to pop what cause a segfault
